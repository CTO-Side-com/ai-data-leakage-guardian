# Provider and service review prompts

Record the exact provider, service/API, deployment/model reference, account/project context, feature set, region/routing and subprocessors. Trace gateways, proxies, embedding and reranking services, fallback models, batch/file APIs, hosted tools, trace exporters and error-reporting vendors independently.

For each sink, obtain a named owner and a service-specific approval reference covering purpose and data classes. Request current documentation and safe configuration evidence for retention, training use, human access/review, optional storage, deletion behavior and geographic processing. Keep dates and scope visible. A marketing statement or another product tier's documentation is insufficient to establish the current application's settings.

Technical data-handling settings, organizational approval and legal/contractual eligibility are separate review items. Do not infer a signed agreement, regulated-data eligibility, residency guarantee, zero retention or zero human access from an SDK, account label, domain or model name. Ask the responsible organizational/legal owner for approval where appropriate; this tool does not make legal determinations.

Review whether enabled features change the boundary: stored conversations, uploaded files, hosted retrieval/vector stores, long-running or batch operations, debugging, abuse monitoring, support exports and provider-operated tools. Check defaults through current official service documentation and authorized configuration evidence rather than recalling them from memory.

During an incident, preserve approved references and minimal necessary metadata. Do not solve a disclosure concern by copying actual sensitive prompts into another AI provider or public issue tracker. Use synthetic reproductions and the organization's authorized incident process.
